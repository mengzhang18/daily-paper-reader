## 摘要
在这篇愿景论文中，我们提出了一种新颖的架构范式，通过统一的编译执行策略来加速AI查询执行。通过将混合AI查询作为一个整体进行编译——将标准SQL关系结构和LLM推理层集成到一个统一的张量计算图中——我们完全消除了跨执行边界的PCIe数据移动瓶颈，并实现了全局编译器优化和高效的自动分片。我们在SemBench Reviews和Movies数据集上对选定和扩展的AI查询展示了这种统一执行范式的可行性，在TPU上实现了高达5.3倍的延迟加速和9.8倍的吞吐量加速，并概述了实现这一愿景的开放技术挑战研究路线图。

## Abstract
In this vision paper, we propose a novel architectural paradigm for accelerated AI query execution via a unified compiled execution strategy. By compiling the hybrid AI Query as a whole -- integrating both standard SQL relational constructs and LLM inference layers into a single, unified tensor compute graph -- we completely alleviate PCIe data movement bottlenecks across execution boundaries and enable global compiler optimizations and efficient automatic sharding. We demonstrate the viability of this unified execution paradigm on select and extended AI queries on SemBench Reviews and Movies datasets, achieving up to 5.3x latency speedup and 9.8x throughput speedup on TPUs, and outline a research roadmap of open technical challenges to realize this vision.

## 1. 核心问题与整体含义（研究动机与背景）

随着大语言模型（LLM）的普及，数据分析系统中出现了大量**AI 查询（AI Query）**——即传统 SQL 关系操作与 LLM 语义算子（如语义分类、语义提取）混合的查询。然而，当前系统普遍采用**分离执行模型（split execution model）**：

- **传统 SQL 操作**在 CPU 或独立数据库引擎上执行；
- **LLM 推理**被卸载到单独的 ML 推理系统（如 vLLM），通常运行在远程机器或独立加速器（GPU/TPU）上。

论文指出这种架构带来了**双重的性能代价**：

1. **严重的数据移动开销**：中间结果必须在数据库引擎的主机 DRAM 与推理引擎的高带宽内存（HBM）或网络附加的远程计算资源之间反复传输。这种跨 Host-To-Device (H2D) 边界的数据搬移在 AI 时代演变为 **"数据移动墙"（Data Movement Wall）**——数据搬运的成本超过了专用硬件加速带来的收益。
2. **优化壁垒（Optimization Hurdle）**：SQL 优化器看不到下游的神经网络操作，ML 编译器也不了解上游的关系上下文，导致跨边界的全局优化（如 SQL 与 AI 算子融合）无法实施。

论文的核心洞察是：**既然现代 LLM 推理本质上就是张量计算图（tensor compute graph），那么可以将标准关系数据库操作（扫描、过滤、聚合等）也降落到同一张量计算图中。** 将关系结构和神经层统一到一个可执行程序中，借助现代 ML 编译器基础设施（如 JAX、MLIR），将整个混合查询编译成一个针对专用硬件（TPU/GPU）的单一可执行文件。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想

将混合 AI 查询**作为一个整体编译**为统一的张量计算图，消除执行边界，实现全局编译器优化和自动多设备分片。

### 2.2 翻译与映射机制（SQL → JAX）

系统先将 SQL 文本解析为抽象语法树（AST），再根据规则将各 SQL 子句映射为标准的 JAX 函数/原语。关键映射如下表所示：

| SQL 子句/算子 | 物理翻译 | 编译的 JAX 实现 |
|---|---|---|
| FROM 表 | 输入数组加载 | 输入张量（input_ids、attn_mask、values_a）打包到分片内存 |
| WHERE values_a < 0.2 | 布尔掩码 | 向量化 JAX 布尔掩码数组 |
| AI_IF(text_col) = 1 | LLM 分类 | Flax 因果 LM 前向传播，比较 "Yes"/"No" 的 logits 生成布尔谓词 |
| AI_TRANSFORM(text_col) | LLM 生成 | Flax 因果 LM 前向传播配合生成式解码，通过 jnp.where 和 pad_id 分片和掩码 |
| SELECT SUM(values_a) | 掩码聚合 | 向量化求和：jnp.where(final_predicate, values_a, 0.0).sum() |

### 2.3 H2D 边界整合

统一执行后，关系过滤谓词、LLM 前向传播（语义分类）和最终 SUM 聚合全部在 TPU 上完成，**不再需要将 logits 或中间数组复制回主机**。以 Gemma-2B 为例（batch size=128，序列长度=32），基线需要将约 **1GB 的输出 logits** 通过 PCIe 拷贝到 CPU 内存，而统一策略只拷贝最终单个标量结果（或最终生成的 token），**将 D2H 传输数据量从 GB 级降至 KB 级**，彻底消除 PCIe 瓶颈。

### 2.4 关键工程细节

- **前端代码生成**：编译器读取 SQL AST，提取关系谓词、UDF（AI 算子）名称和表定义，从 UDF 注册表中检索匹配的 JAX/Python 模板文件，插入到全局 JAX 程序模板中。
- **控制流优化**：利用 JAX 的 `jax.lax.scan` 表达循环结构（如逐批次流式处理），避免将循环展开为庞大静态程序，通过 TPU 寄存器维护中间状态。

## 6. 主要结论与发现

1. **统一编译执行在可行性上得到验证**：将混合 AI 查询编译为单个统一的 JAX 程序在技术上可行，且能产生显著性能收益。
2. **性能提升显著**：在 TPU 上实现高达 **5.3 倍延迟加速** 和 **9.8 倍吞吐加速**（Q1 与选择性实验）。
3. **数据移动是分水岭**：交叉连接场景中，H2D 传输从 3.9 GB 降至 3.9 MB（N=2000）；长序列调试输出场景中 D2H 从全量传输降至仅匹配项。
4. **自动分片带来线性扩展**：编译器的 PMAP/GSPMD 自动分片使 4 设备扩展达到完美线性（4.00x），无需手动编写并行化逻辑。
5. **高选择性查询仍是短板**：当关系过滤器能提前跳过大部分数据时，分离执行模型具有优势（Q3 在高选择性下统一方案延迟反而更差）。
6. **多租户并发存在瓶颈**：TPU 执行队列串行化导致吞吐恒定不变，需要运行时调度器支持动态调度。

## 7. 优点

- **范式创新**：提出并实现了将 SQL 关系操作与 LLM 推理统一编译的架构范式，突破了传统分离执行的性能壁垒。
- **实用价值明确**：量化了跨边界数据移动的具体代价（GB 级 logits 拷贝），证明统一执行在大数据量传输场景下的巨大优势。
- **与现有生态兼容**：基于 JAX/XLA 构建，直接利用成熟 ML 编译器基础设施，而非从零实现数据库系统。
- **实验设计合理**：包含选择性扫描、横向扩展、多租户等维度，对统一执行的优缺点进行了较客观的呈现。
- **诚实披露不足**：明确承认 Q3 高选择性场景下基线表现更优，并列入研究路线图。

## 8. 不足与局限

- **实验覆盖有限**：仅覆盖单节点 4 设备，未评估多节点扩展；数据集规模（49,664 行）相对较小。
- **高选择性查询性能退化**：统一的静态编译和固定 micro-batch 处理导致全表扫描，无法在设备端动态跳过不相关数据。
- **多租户并发瓶颈未解决**：当前多租户吞吐无法随并发提升，限制了企业级高吞吐场景的应用。
- **动态形状支持不足**：目前通过 padding 到静态最大序列长度，浪费 TPU 内存和计算资源。
- **多模态算子缺失**：未支持图像、音频、视频等多模态数据，而 SemBench 原生场景包含视觉语言模型（VLM）需求。
- **成本模型缺失**：未建立语义感知的代价优化模型，无法动态权衡区分执行与统一执行的优劣。
- **与基线比较的公平性**：基线缺乏跨引擎并行化优化（如 CPU 多核并行 + TPU 多设备并行），可能低估了分离执行的最佳性能。
