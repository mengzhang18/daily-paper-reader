## 摘要
从自然语言查询接口到自动化报告生成，数据分析工具需要数据的描述：其中包含的真实世界实体，哪些列作为度量或标识符，以及表如何连接成分析单元。如今，这一语义层通常由手工编写。这是一个知识获取瓶颈，限制了分析系统的可扩展性，使非技术用户依赖专家，并且本身容易出错。我们提出TYTAN，一个从关系数据库以及（如果可用）用户提供的简短描述中自动构建分析语义模式的系统。TYTAN将数据库的符号分析与基于LLM的语义推断相结合，用于实体提议、角色分配和命名。当证据使决策存在歧义时，TYTAN会向用户提出一个有针对性的自然语言问题。我们在八个跨越真实世界和基准领域的数据库上评估TYTAN，沿定义模式功能效用的三个维度：（i）覆盖率，是否捕获了所有重要实体和特征？（ii）检索正确性，模式的指令是否真正到达数据？（iii）表征准确性，语义类型是否正确？在七个参考领域中，TYTAN达到了专家修正的参考模式中的每个实体、属性和可聚合特征（100%覆盖率）。此外，其100%的检索指令正确执行（1,678/1,678个自生成声明），语义角色在与参考模式匹配的属性中有92%至100%一致。对底层数据的检查表明，小的分歧在于参考模式，而不是TYTAN。在一个留出的盲测中（一个具有十张表且无声明键的实时数据库），TYTAN恢复了完整的实体结构并验证了键，满足了五位独立盲评者对可满足期望的100%。

## Abstract
From natural-language query interfaces to automated report generation, data analysis tools need a description of the data: the real-world entities it contains, which columns function as measures or identifiers, and how tables connect into units of analysis. Today, this semantic layer is usually written by hand. This is a knowledge-acquisition bottleneck that limits the scalability of analytic systems, keeps non-technical users dependent on experts, and is itself error-prone. We present TYTAN, a system for automatically constructing an analytic semantic schema from a relational database and, when available, a short user-provided description. TYTAN combines symbolic analysis of the database with LLM-based semantic inference for entity proposal, role assignment, and naming. When the evidence leaves a decision ambiguous, TYTAN asks the user a targeted natural-language question. We evaluate TYTAN on eight databases spanning real-world and benchmark domains along the three axes that define a schema's functional utility: (i) coverage, are all important entities and features captured?; (ii) retrieval correctness, do the schema's instructions actually reach the data; and (iii) characterization accuracy, are semantic types correct? Across the seven reference domains, TYTAN reaches every entity, attribute, and aggregable feature of the expert-corrected reference schemas (100% coverage). Additionally, 100% of its retrieval instructions execute correctly (1,678 of 1,678 self-generated claims), and semantic roles agree with the reference on 92-100% of matched attributes. Checking the underlying data showed the small disagreement is in the reference, not in TYTAN. On a held-out blind test (a live, ten-table database with no declared keys), TYTAN recovers the full entity structure with verified keys and satisfies 100% of the satisfiable expectations of five independent blind annotators.

- **问题背景**：数据分析工具（自然语言查询接口、自动化报告生成、BI 工具等）需要一种“语义层”来描述数据的业务含义，包括真实世界实体、哪些列是可聚合的度量或标识符、表与表之间如何连接成分析单元。当前这类语义层通常由人工编写。

- **整体含义**：该论文旨在解决上述瓶颈，使得从关系数据自动构建“分析语义模式”成为可能，从而提升分析系统的可扩展性、可靠性和易用性。其成果可服务于自然语言查询、语义层构建、报告生成等多种下游应用。

### 2. 论文提出的方法论

**核心思想**：TYTAN 采用“神经符号”（neurosymbolic）混合架构，将 LLM 的语义推断能力与数据库的确定性符号分析相结合，在保证语义灵活性的同时，用数据事实约束模型幻觉，并在证据不足以决策时引入人类反馈。

**关键技术细节与流程**（分为三阶段）：

1. **符号分析与结构化画像（Structural profiling）**：
   - 从数据库中采集确定性信息：表、列、已声明的主外键、列值样本、基数、空值率、列类型等。
   - 支持 CSV/Excel 等无约束文件，加载为关系存储后同样处理。

2. **LLM 驱动的语义推断与接地验证**：
   - **实体提议与接地**：LLM 基于数据描述和画像结果提出实体及属性，然后与真实表列匹配；重复实体合并；未分配表按实体、链接表、传递表、忽略四类分类；未分配列补入实体。
   - **连接发现与验证**：已声明外键直接采用；未声明连接候选经过多重检查：
     - 值重叠检查（全量去重值，无重叠即拒绝）；
     - 确定性键角色守卫（排除主键列、数值度量列、已有引用列、多候选重叠列等）；
     - LLM 语义验证（基于列名/类型/样本判断，置信度需超过阈值）。
   - **类型标注**：区分物理存储类型（isa）与分析角色（type：Categorical / Numeric / Metric / Datetime / Identifier）。证据可以修正角色，但不能覆盖语义（如数字邮编仍是 Categorical）；可计算的事实直接从数据库计算（如声明类型、唯一性验证）。
   - **键验证**：声明的键被接受，未声明的候选键需通过唯一性测试，否则搜索其他候选；复合键也纳入考虑。
   - **命名与表面形式**：生成人类可读的名称、描述和引用模板；校验模板中的占位符是否指向真实属性。

3. **交互式澄清循环（Clarification loop）**：
   - 当数据库证据不足以解决歧义（如表角色、列映射、语义类型）时，TYTAN 向用户提出针对性自然语言问题，并根据回答重建相应部分。
   - 每个问题都有默认答案，支持完全无人值守运行。

**输出格式**：称为 **ring** 的自包含 JSON 语义目录，包含实体（含已验证 ID）、属性（含来源、存储类型、分析角色）、连接路径、聚合属性路径、语言表面形式（名称、描述、引用模板）等，可直接被下游分析平台（如 SATYRN）消费。

### 7. 优点

- **神经符号结合设计**：LLM 提供语义推断，符号分析提供事实校验，二者互补。关键决策（键唯一性、值重叠、列存在性）完全依赖确定性验证，消除了 LLM 幻觉对模式的不可逆污染。
- **人类反馈机制**：仅在证据不足且影响重要的场景下提问，且每个问题有默认答案，支持全自动运行，兼顾可用性与可靠性。
- **功能导向的评估框架**：将评估定义在“覆盖-检索-表征”三个功能性维度，避免仅以结构相似度衡量；并通过执行 ring 中的指令来验证其可操作性，而非只看名称匹配。
- **盲测设计严谨**：期望清单提前冻结、独立于系统生成，且保留“不可满足项”（数据中不存在的期望），使召回率计算更准确。
- **元数据消融**：直接验证系统在无约束 CSV 场景下的鲁棒性，并揭示连接发现的边界条件。
- **输出格式系统无关**：ring 不绑定特定平台，但被证明兼容端到端下游系统（SATYRN），展示了实际可用性。
- **对偶缺陷审计**：采用多模型 + 人工复核的审计流程，减少单一模型偏见。

### 8. 不足与局限

- **数据形态限制**：仅支持关系型和扁平表格数据，对 JSON、事件日志等需要先扁平化，可能丢失结构；知识图谱等图状数据源不在范围内。
- **连接发现保守**：当一方存 ID、另一方存名称等异构表示时，T YTAN 可能错过真实关系；值重叠检查依赖全量数据访问，若仅提供样本则可靠性下降。
- **实体多引用结构的不完整支持**：一对表之间的多个外键虽然都保留，但在计算聚合属性时只遍历其中一条路径，尚未支持并行连接的多路径遍历。
- **复合键发现能力弱**：缺少声明外键时，复合键候选生成受限（文中提到的一个失败案例即由此引起）。
- **用户澄清循环未单独评估**：系统在无人值守模式下运行整体表现好，但每个默认答案的质量、用户交互的有效性、回答错误时的鲁棒性都没有测量。
- **参考模式的潜在偏差**：专家参考模式由作者团队为同一下游系统编写，可能隐含对特定消费系统的适配；对其他下游系统的泛化尚未测试。
- **计算成本**：剥离元数据后构建成本增加约 5 倍；大模式会增加 LLM 验证调用数量，在运行时间和 API 成本上不可忽略。
- **评估客观性局限**：无现有基线方法对比（如单纯 LLM 生成或用传统依赖发现方法），无法量化 TYTAN 相对简单替代方案的相对优势；LLM 盲评者与自身生成器同源可能系统性高估语义合理性。
