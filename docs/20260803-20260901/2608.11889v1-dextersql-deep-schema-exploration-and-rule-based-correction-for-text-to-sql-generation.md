## 摘要
基于提示（即非微调）的Text-to-SQL方法，其中底层大语言模型参数不因任务而改变，面临三个问题：（i）依赖粗粒度的模式信息，可能无法揭示区分模糊列所需的细粒度关系；（ii）未捕获重复出现的SQL生成失败；（iii）在复杂问题中遭受条件遗漏、幻觉或错位。本文开发了DexterSQL，一个基于提示/非微调的Text-to-SQL系统，通过三个新组件改进SQL生成：（i）深度模式探索器，识别模糊列，分析它们的个体和联合数据分布，以揭示它们之间的关系及各自的不同作用；（ii）数据库无关的规则创建器，仅在训练数据库上挖掘生成SQL与金标准SQL之间的不匹配，并将其转化为数据库无关的校正规则，捕获重复的LLM失败模式；（iii）多路径SQL生成，引入基于依赖树的中间表示，利用问题的句子结构指导其分解为SQL骨架，以进行最终SQL生成。与最先进方法相比，DexterSQL在使用开源/权重和闭源/权重模型时均实现了更高准确率。特别是，DexterSQL在使用开放权重模型（GPT-OSS-120B）时，在BIRD-Dev上显示出至少2.7%的高提升，总准确率达到67.6%。DexterSQL在使用闭源权重模型时也显示出至少0.9%的更好提升，在BIRD-Dev上使用GPT-4o和GPT-5.2时总准确率分别为71.6%和72.2%。”}

## Abstract
Prompting-based (\textit{i}.\textit{e}., non-fine-tuning) Text-to-SQL methods, where underlying large language model parameters are not changed for the task, face three problems: (\textit{i})~relying on coarse-grained schema information that may not reveal the fine-grained relationships needed to distinguish ambiguous columns, (\textit{ii})~not capturing recurring SQL-generation failures, and (\textit{iii})~suffering from omission, hallucination, or misplacement of conditions in complex questions.   This paper develops \textsc{DexterSQL}, a prompting/non-fine-tuning-based Text-to-SQL system that improves SQL generation with three novel components: (\textit{i})~\emph{deep schema explorator} that identifies ambiguous columns, analyzes their individual and joint data distributions to uncover their relationships and the distinct role of each, (\textit{ii})~\emph{database-agnostic rule creator} that mines mismatches between generated and gold SQL only on the training database and converts them into database-agnostic corrective rules that capture recurring LLM failure patterns; and (\textit{iii})~\emph{multi-path SQL generation} that introduces a dependency-tree-based intermediate representation that uses the question's sentence structure to guide its decomposition into an SQL skeleton for final SQL generation.   \textsc{DexterSQL} achieves a higher accuracy compared to the state-of-the-art using both open-source/weight and closed-source/weight models. Particularly, \textsc{DexterSQL}'s shows a high improvement of at least 2.7\% using an open-weight model (GPT-OSS-120B) on BIRD-Dev, with total accuracy 67.6\%. \textsc{DexterSQL} also shows better improvement of at least 0.9\% using closed-weight models, with total accuracy 71.6\% and 72.2\% on BIRD-Dev with GPT-4o and GPT-5.2.

## 一、核心问题与整体含义

- **研究背景**：Text-to-SQL 任务旨在将自然语言（NL）问题转换为可执行 SQL 查询。早期基于专门神经架构（如编码器-解码器）的方法因需针对每个数据集单独训练，鲁棒性差；近期基于 LLM 的方法虽大幅提升了性能，但可划分为微调（fine-tuning）与非微调（prompting-based / non-fine-tuning）两种范式。本文聚焦后者，即不改变 LLM 参数，仅通过提示词、模式链接、分解与校正来完成任务。
- **核心问题（三大挑战）**：
    - **C1（模式信息粗粒度）**：现有方法依赖粗粒度的模式信息（如仅分析列名、样例值或元数据），难以识别模糊列（如不同表中同名但语义不同的列），导致选错表或列。
    - **C2（无法捕获重复失败）**：LLM 在 SQL 生成中存在重复性错误（如整数除法截断），现有系统无法将这类可复用的失败模式从数据库特定错误中分离并转化为通用修正规则。
    - **C3（复杂问题条件处理不佳）**：LLM 在分解复杂 NL 问题时，可能遗漏、幻觉或错位关键条件，使生成的 SQL 回答问题不完整或错误。
- **论文含义**：提出 DexterSQL——一个无需微调、即可显著提升 SQL 生成准确率的系统，通过深度模式探索、数据库无关规则学习、多路径生成三种机制，在开源与闭源模型上均超越了当时的最先进（SOTA）方法。

## 二、方法论

DexterSQL 整体分为四个阶段，其中 Phase 1 为离线预处理，Phase 2–4 为在线推理。核心贡献是三个新组件，分别对应上述三大挑战。

- **Phase 1：预处理（离线执行一次）**
    - **（一）深度模式探索器（Deep Schema Explorator）**：解决 C1。
        1. **候选对生成**：通过列名 token 重叠或列画像 embedding 相似度，识别可能歧义的列对（如 `Patient.Diagnosis` 与 `Examination.Diagnosis`），并排除被 PK/FK 结构已明确定义的列对。
        2. **LLM 三阶段筛查**：分别在「仅画像」「画像+PK/FK」和「完整上下文」三种提示下要求 LLM 判断该列对是否可能让 SQL 生成模型选错，多数投票决定是否保留。
        3. **深度调查**：对确认的歧义列对，计算**个体分布**（null 数、不同值数、Jaccard 重叠度）与**连接条件分布**（若存在 PK/FK 连接路径）：
            - **覆盖率**：`coverage = |π(join)| / |π(T_i)|`
            - **扇出**：`fanout = |join| / |π(join)|`
            - **一致性**：`agreement = |σ(col_i=col_j)(join)| / |join|`
        4. **笔记合成**：将证据用 LLM 浓缩为一句结构化消歧笔记（如“`Patient.Diagnosis` 是患者的最终诊断，用于患者级问题；`Examination.Diagnosis` 是每次检查的初步诊断，用于检查级问题”）。
    - **（二）数据库无关规则创建器（Rule Creator）**：解决 C2。
        1. **错误挖掘**：在训练数据库上采样问题，让 LLM 生成候选 SQL（多次采样），执行后与金标准 SQL 结果不一致的候选保留，并由 LLM 解释失败原因。
        2. **数据库无关过滤**：用 LLM 区分解释是否与特定库/表/列绑定，丢弃数据库特定错误（如选错列），保留可泛化的 SQL 构造错误（如缺少浮点转换）。
        3. **错误聚类**：在库内用层次聚类，再跨库合并同源错误，形成主导错误组。
        4. **规则合成**：将每个主导组转化为规则 `rule = <gist, bad-pattern, correct-pattern, fix>`（如：`SUM(a)/SUM(b)` → `CAST(SUM(a) AS REAL)/SUM(b)`）。
    - **（三）Column Profiler 与 Index Generator**：为每列构建画像（基数、代表值、最频繁值等），并构建**画像向量索引**和**值向量索引**，为在线模式链接提供检索基础。
- **Phase 2：模式链接（在线）**：先用索引检索构建初步聚焦模式（Focused′），再用 LLM 生成初步 SQL（基于三种不同 prompt），据此识别缺失列并补充，形成最终聚焦模式。
- **Phase 3：SQL 生成（在线）**：解决 C3。
    - **Note Incorporator**：从全局笔记集中筛选与当前问题相关的笔记，并可能把笔记中的另一列补充进聚焦模式。
    - **三路并行生成器**：
        1. **依赖树中间表示生成**（本文核心创新）：用确定性解析器（如 Python NLTK/SpaCy 等）生成 NL 问题的依赖树，将问题中的元素（实体、字面量、关系）映射为 SQL 组件骨架（如 `WHERE ID=1 AND Diagnosis='PSS'`），LLM 用该骨架生成最终 SQL。
        2. **Few-shot in-context learning**：检索结构相似的问题-查询对，作为示例。
        3. **Divide-and-conquer**：将复杂问题分解为子问题，分别生成子 SQL 再组合。
- **Phase 4：SQL 修正与选择（在线）**：
    - **修正**： ① SQLGlot 语法检查 + 执行反馈生成诊断报告；② 用 LLM 根据诊断报告修正（`revise SQL`）；③ 判断是否需要规则修正，从规则集 `Rule` 中选取相关规则；④ 应用规则生成校正后的候选集。
    - **选择**：执行所有候选按其返回结果聚类。若最大簇置信度 `Conf(s_i) = |Cluster_i|/|correct SQL|` 超过阈值（实验最优为 0.6），直接返回代表查询；否则用 LLM 对 top-K 簇代表逐一配对比较，结合比较胜出次数与执行置信度选出最终 SQL。

## 七、优点

- **针对性强**：三个核心组件精确对应三类明确的问题（粗粒度 schema、重复错误、分解失败），设计逻辑紧密，而非通用的 prompting“技巧堆叠”。
- **深度数据探索**：在数据分布层面（个体分布、连接条件分布）识别列间关系，比仅依赖命名或嵌入相似性的方法更根本地消解列歧义，且通过“LLM 三阶段筛选”控制探索成本，避免了枚举所有列对的不可扩展性。
- **数据库无关规则**：从训练库挖掘可迁移到任意目标库的失败模式，同时丢弃库特定错误，使规则具备良好通用性。
- **确定性结构 + LLM 灵活性的结合**：依赖树是确定性解析，骨架映射保留问题的结构与字面量，能有效防止条件遗漏/幻觉。
- **多路径互补策略**：将新方法与成熟的 few-shot、divide-and-conquer 并行，显著扩大候选池多样性（UB-EX 提升 2.7%），并通过执行聚类与置信感知选择保证最终候选可靠性。
- **适用性广**：同时在开源、闭源模型上验证，且强调本地部署场景（隐私/安全），适合敏感数据场景。
- **执行效率兼顾**：不仅追求准确率，还报告了 VES，表明生成 SQL 的执行开销在可接受范围内甚至更优。

- **对比公平性风险**：部分最先进对比（CHESS、DSR-SQL、AutoLink、SuperSQL 等）使用原论文报告数据而非同一环境重跑；即使本地跑的方法也仅对比了“强竞争者”而非全部方法（如 GPT-5.2 上只与 APEX-SQL 与 DeepEye-SQL 比较），可能引入不一致。
- **阈值调优可能过拟合**：置信阈值 0.6 是在 BIRD-Dev 上取最优，未说明在 Spider 或其它数据集上的迁移性，存在对基准的调优风险；不确定性度量仅基于执行结果聚类与内部一致性，而非真实正确性。
- **规则创建的冷启动依赖**：需要预先存在带金标准 SQL 的训练数据库，若新领域缺乏标注数据，则 Rule Creator 的规则无法生成。
- **多路径生成的计算开销**：三路并行本就增加采样次数，再加上 LLM 评审选择，推理延迟与成本较高，论文未分析时间/金钱开销。
- **错误分析缺失**：未对失败案例做系统性分析（如哪类问题在什么情况下仍失败），也未讨论幻觉来源的深层原因。
- **评价指标局限**：仅使用 BIRD-Dev 与 Spider 测试集，未包括更复杂的领域（如表格、数据库维护或长尾分布）、未考虑语义等价但执行结果不同的 SQL；也未报告哪些错误案例在规则修正后被挽救的细节。
