## 摘要
直接文本到SQL要求语言模型完成两项工作：解释业务问题并构造完整的关系查询。在企业模式中，SQL可能成功执行，但使用了错误的关系角色或聚合粒度。我们研究随机边界的另一种放置方式。多轮规划器将短语落地，并从问题特定的受控选项中进行选择；图遍历、角色谓词、粒度降低、SQL构造和确定性检查均在代码中实现。我们在ACME保险基准上，将这种语义路径编译（SPC）系统与直接DDL到SQL生成进行对比评估。在包含38个问题、每个问题运行三次的裁定比较集上，SPC在37个问题（97.4%）的每次运行中均被裁定正确，而基线为21个（55.3%）。配对不一致结果为：16个问题支持SPC，没有问题支持基线（双侧精确McNemar检验p=3.05×10^-5）。SPC在114次运行结果中，38个问题至少正确回答一次，并产生一次拒绝，没有出现被裁定为错误但已执行的运行；基线在同一集合上产生了29次被裁定为错误的运行，以及另外7次被评审标记的仅数据巧合。严格等价敏感性分析增加了配对差异。使用GPT-5.4和Gemini-3.6-Flash进行的额外SPC运行显示出类似的问题级鲁棒性，尽管其每次运行的判定产物未被保留。在全项目分析中保留了六个额外的基准项目，并按失败类别单独记录。该研究支持端到端系统的结果，而不是因果断言“仅编译就产生了收益”，因为SPC接收到了DDL基线未收到的受控语义产物。

## Abstract
Direct text-to-SQL asks a language model to do two jobs: interpret the business question and construct the complete relational query. In enterprise schemas, SQL can execute successfully while using the wrong relationship role or aggregation grain. We study an alternative placement of the stochastic boundary. A multi-turn planner grounds phrases and selects from question-specific governed options; graph traversal, role predicates, grain lowering, SQL construction, and deterministic checks are implemented in code. We evaluate this semantic path compilation (SPC) system against direct DDL-to-SQL generation on the ACME insurance benchmark. On a 38-question adjudicated comparison set with three runs per question, SPC was adjudicated correct on every run for 37 questions (97.4%), compared with 21 (55.3%) for the baseline. The paired discordance was 16 questions in favor of SPC and none in favor of the baseline (two-sided exact McNemar p=3.05x10^-5). SPC answered all 38 questions correctly at least once and produced one refusal and no adjudicated wrong-but-executed run across 114 run outcomes; the baseline produced 29 adjudicated wrong runs and seven additional judge-flagged data-only coincidences on the same set. A strict-equivalence sensitivity analysis increased the paired difference. Additional SPC runs with GPT-5.4 and Gemini-3.6-Flash showed similar question-level robustness, although their per-run verdict artifacts were not preserved. Six additional benchmark items are retained in an all-item analysis and documented separately by failure class. The study supports an end-to-end systems result, not a causal claim that compilation alone produced the gain, because SPC receives governed semantic artifacts that the DDL baseline does not.

## 1. 核心问题与整体含义

- **研究动机**：直接文本到 SQL（Text-to-SQL）通常让语言模型同时承担“业务语义解释”和“SQL 构造”两项任务。在企业数据库中，SQL 可能执行成功且返回数字看似合理，但实际使用了错误的关系角色（如将保单持有人与代理人混淆）或错误的聚合粒度（如未对多路径扇出进行预聚合），导致“正确执行但语义错误”的结果。
- **核心问题**：能否通过重新划分“随机边界”——让语言模型只负责语义落地与选择，而将图遍历、角色谓词、粒度降低、SQL 构造和静态检查全部交给确定性代码——显著提升企业级 Text-to-SQL 的重复运行可靠性？
- **整体含义**：本文提出“语义路径编译”（Semantic Path Compilation, SPC）系统，将随机行为限制在“有界语义规划”内，其余关系实现全部由确定性引擎完成，追求的不仅是正确率，更是失败模式的可控性（拒绝而非错误执行）。

## 2. 方法论

### 核心思想
- 将语言模型的能力限定为：从问题中引用原文片段、选择系统返回的受控语义标识符、在有限的问题特定候选项中进行取舍。
- 语言模型不能直接命名表、列、连接谓词、角色谓词或 SQL 片段；所有关系路径、角色绑定、粒度变换和 SQL 生成均由确定性编译器完成。

### 关键流程
1. **多轮规划器（Planner）**：对问题短语进行分解和绑定，调用确定性检索工具。工具返回的是“路径不透明、不可组合”的路由句柄（如 `Policy>PolicyAmount#4`），模型只能选择，不能编辑。
2. **受控语义模型与物理映射**：作者编写了 ACME 业务本体（概念、角色、边、指标）与物理映射（表、键、谓词），加载时通过 8 条验证规则确保模型完全绑定。
3. **确定性解析与路由枚举**：解析器将问题短语映射到受控概念；图枚举器按治理约束、角色有效性、支持度和跳数上限，确定性枚举所有可管理路径，并按规范顺序返回句柄。
4. **确定性审查与重试**：`review_plan` 检查草稿是否遗漏必要指标/属性、是否错误投影独立扇出分支；提交后引擎再次独立审查，失败则拒绝。被拒后最多允许一次全新重试（仅携带拒绝原因）。
5. **粒度感知 SQL 编译**：采用“主干+卫星”布局——每个输出分组一行；每个度量在自身支持的源粒度单独计算（卫星），再聚合回主干，避免独立度量行互相放大。角色谓词由类型化边强制生成（如 `Party_Role_Code='PH'`），不可省略或改写。
6. **静态检查**：解析 SQL 并检查已知治理违规；无法确定的情况标记为 `undecidable` 不阻断，但确定性验证的违规会阻断 SQL 发布。

### 确定性契约
- 最终 SQL 是「已接收计划 + 本体 + 物理映射 + 编译器版本」的确定性函数。
- 模型可见的符号集合是有限且问题特定的（由检索结果构造 JSON Schema 枚举），从而防止普通结构化提交引用未检索对象。

## 3. 实验设计

### 数据集 / 基准
- **ACME 保险基准**：源自 Sequeda、Allemang、Jacob 提出的企业知识图谱问答基准 [Sequeda]，并使用 dbt 的 ACME 改编版 [dbt-2026]。
- 基准共有 **44 个问题标识符，实际物化 43 个问题**；研究使用 SQLite 移植版数据库，保留源参考 SQL（除注释规范化）。
- 主配对比较集为 **38 个问题**，另有 6 个问题因参考 SQL 缺陷或执行端口不兼容被移入“全项目分析”，按失败类别记录（参考扇出陷阱 2 项、SQLite 整数除法不兼容 2 项、不兼容函数 DATE_DIFF 1 项、过度投影/问题范围争议 1 项）。

### 对比方法与实验场景
- **基线 B0**：直接 DDL-to-SQL。模型接收数据库 DDL 与问题，直接生成 SQL；没有本体、编译器或拒绝机制。
- **SPC 系统**：有界语义规划 + 确定性编译，接收作者编写的本体与物理映射。
- **数据反事实（Counterfactual）测试**：构造反事实数据库实例，在保持业务事实不变的情况下改变关系多重性，用于区分“在原始实例上偶然一致但在语义上错误的查询”。
- **模型多样性测试**：SPC 分别使用 `gpt-5.6-luna`、`gpt-5.4`、`gemini-3.6-flash` 三种规划器，采用相同 3 次运行协议；但只有 Luna 有配对基线。

### 评估协议
- 每个问题运行 3 次；问题级“稳定成功”需全部 3 次成功。
- 执行后，先进行确定性比较；不一致问题由 `gpt-4o` 以最多 3 次投票多数裁决，判定类别包括 `equivalent`、`superset`、`prediction_wrong`、`agrees_on_this_data_only` 等。
- 主要统计检验为双侧精确 McNemar 检验；并发Wilson 95% 区间描述单臂比例。
- 敏感性分析包括：只计 `equivalent` 为成功的严格评分；将 `agrees_on_this_data_only` 全部视为成功（保守方向）；以及包含全部 44 个项目的全项目分析。

## 6. 主要结论与发现

- **主配对结果（38 题）**：
  - SPC 稳定正确：37/38（97.4%，Wilson 95% CI [86.5, 99.5]）；B0 为 21/38（55.3% [39.7, 69.9]）。
  - SPC 至少一次成功：38/38（100%）；B0 为 31/38（81.6%）。
  - 运行级别：SPC 114 次运行中 113 次正确、1 次拒绝、0 次“错误但已执行”；B0 114 次运行中 78 次成功、29 次裁定错误、7 次“仅数据一致”标志、0 次拒绝。
  - 配对不一致：16 题支持 SPC、0 题支持 B0；双侧精确 McNemar p = 3.05×10⁻⁵。
- **严格敏感性分析**：只计 `equivalent` 为成功时，B0 降至 18/38（47.4%），SPC 仍为 37/38；配对不一致变为 19:0，p = 3.81×10⁻⁶。若将“仅数据一致”都算成功，B0 升至 22/38，SPC 仍 37/38，p = 6.10×10⁻⁵。结论方向不变。
- **模型鲁棒性**：GPT-5.4 SPC 稳定成功 36/38（94.7%）、Gemini-3.6-Flash 为 35/38（92.1%），与 Luna 的差距均在两个问题以内。
- **全 44 项目保守分析**：SPC 稳定成功 38/44（86.4%），B0 为 22/44（50.0%）；配对不一致 17:1 支持 SPC，p = 1.45×10⁻⁴。
- **反事实证据**：验证了“粒度不安全查询在原始实例与参考一致、但在反事实实例上分歧”的机制，支持所枚举缺陷的可分离性。
- **总体判断**：SPC 将随机性从 SQL 构造重定位到有界语义规划，系统级可靠性显著高于直接 DDL-to-SQL 生成；但该项收益来自“受控语义知识 + 有界接口 + 确定性编译 + 重试策略”的整体组合，不能归因于单独某一机制。

## 7. 优点

- **边界设计清晰**：明确区分“随机语义决策”与“确定性关系实现”，语言模型能力被限定在可审计、可治理的范围内。
- **失败模式更可控**：SPC 在无法处理时选择拒绝，而不是返回可执行的错误结果；这比“错误执行”更有利于企业风险管控。
- **粒度与角色处理有理论支撑**：引用 summarizability、grain theory、eager aggregation 等既有工作，并实现了具体的编译器策略（主干-卫星布局）。
- **评估注重可靠性而非单一准确率**：重复运行、稳定成功/至少一次成功、拒绝与错误执行分离；双侧精确 McNemar 检验适合配对设计。
- **反事实数据设计**：专门构造“同结果但语义不同的查询可分离”的数据库实例，增强了对偶然一致错误的甄别能力。
- **透明度较好**：论文明确讨论偏差来源、未披露信息、无法复现的部分，并公开部分代码与模型文件。

## 8. 不足与局限

- **单一领域与基准规模**：仅 ACME 保险领域、44 个问题、38 个配对问题；样本量小，结论不能外推到其他企业域。
- **受控语义知识优势混杂**：SPC 接收了手工编写的本体和物理映射，而 B0 只接收 DDL；因此对比是“完整系统效应”，不能分离“语义知识”与“机制”的贡献。
- **开发与评估同源**：编译器、解析器、检查器在查看基准问题过程中迭代开发，存在基准过拟合风险；没有保留留出组合测试集。
- **评审偏差**：LLM 评审（gpt-4o）决定非确定性一致的裁决，且 `agrees_on_this_data_only` 等类别是主观判断；无独立人工复评。
- **可复现性不足**：作者明确承认当前归档缺少 SQLite 数据库、工作树状态、部分每次运行判定产物等，无法端到端复现；公开代码快照也未包含全部证据。
- **执行协议不对称**：SPC 可重试一次、B0 不可；温度参数等抽样细节未完全保留，影响对“模型随机性控制”的精确对比。
- **静态检查不完全**：`undecidable` 发现不阻断 SQL，因此“零错误执行”不构成普遍正确性保证。
- **计算成本未评估**：论文没有报告推理成本、token 消耗或延迟，因此无法判断该架构在真实部署中的经济性与效率。
